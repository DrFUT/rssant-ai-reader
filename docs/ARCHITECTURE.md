# 架构设计说明

本文档面向「想看懂这个项目是怎么设计的」的读者，补充 README 里没展开的设计决策与取舍理由。

---

## 1. 分层

```
┌─────────────────────────────────────────────────────────────┐
│  表现层     rssant_ai/templates/rssant_ai/reader.html        │
│             零构建步骤的单页阅读器(vanilla JS + fetch)         │
├─────────────────────────────────────────────────────────────┤
│  接口层     rssant_ai/views.py   /api/v1/ai/*                │
│             只做参数解析与序列化, 不含业务逻辑                 │
├─────────────────────────────────────────────────────────────┤
│  任务层     rssant_ai/tasks.py   Celery 任务                  │
│             只管调度语义(超时/重试/计数), 不含业务逻辑          │
├─────────────────────────────────────────────────────────────┤
│  业务层     rssant_ai/service.py                             │
│             唯一同时依赖 ORM 与 ai/ 的地方                    │
├─────────────────────────────────────────────────────────────┤
│  AI 服务层  ai/  纯 Python, 不 import django, 可单独测试      │
├─────────────────────────────────────────────────────────────┤
│  数据层     StoryAI / DailyDigest / UserInterest  +  rssant    │
│             原有的 Story / Feed / UserFeed                    │
└─────────────────────────────────────────────────────────────┘
```

**为什么把 `ai/` 和 `rssant_ai/` 分开？**

`ai/` 不 import 任何 Django 模块，所以它：

- 可以用 `python` 直接跑单测，不需要配置数据库和 settings
- 可以脱离 Web 框架复用到命令行脚本、离线批处理（项目里的 `rssant_cli` 就是这种用法）
- 换 Web 框架（FastAPI 之类）时不用动

代价是多一层间接。对这个体量的项目，这个代价是值得的。

## 2. 数据模型

### 为什么是独立表，而不是往 Story 上加字段？

用户的需求写的是「数据库增加 summary / keywords / ai_score」。实现上选择新建 `StoryAI` 表，理由：

1. rssant 的 Story 查询大量使用 `django-seal` + 字段裁剪（`defer` / `only`）。往主表塞大字段会拖慢**所有**阅读接口的查询，哪怕用户不需要 AI 摘要。
2. AI 结果有自己的生命周期（排队 → 处理 → 失败重试），独立表可以单独建索引、单独限流、单独清理，不影响订阅同步的热路径。
3. 对上游的侵入最小 —— 只加一个外键关联，`Story` 表结构一行没改。

### 表结构

```
StoryAI                          一篇文章的 AI 处理结果
├─ story_id      OneToOne → Story
├─ ai_summary    一句话总结
├─ ai_points     JSON[]   关键观点(3 条)
├─ ai_keywords   JSON[]   关键词/标签
├─ topic         一级主题(AI/技术/编程/商业/科学/娱乐/其他)
├─ ai_score      价值评分 0-10
├─ status        pending|processing|done|failed|skipped
├─ retry_count   已重试次数
├─ error         最近一次失败原因
└─ model         使用的模型名(便于排查与成本核算)

DailyDigest                      每日简报
├─ date          unique
├─ overview      今日概览
├─ items         JSON[]  [{story_id,title,digest,reason,score,link}]
├─ markdown      渲染后的 Markdown
└─ story_count   候选文章数

UserInterest                     用户兴趣配置
├─ user_id       OneToOne → User
├─ keywords      逗号分隔的关注关键词
├─ topics        JSON[]  关注主题
├─ threshold     命中阈值
└─ enable        是否启用
```

索引：`(status, ai_score)`、`(status, dt_created)`、`(topic, ai_score)` —— 分别服务「巡查队列」「积压统计」「主题筛选」三个查询。

## 3. AI 处理状态机

```
                ┌──────────┐
     新建文章 ──►│ pending  │◄──────────────┐
                └────┬─────┘               │
                     │ 被 worker 领取       │ 卡住超过 15 分钟
                     ▼                     │ (worker 被 kill 的僵尸行)
                ┌────────────┐             │
                │ processing │─────────────┘
                └─────┬──────┘
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      ┌───────┐  ┌────────┐  ┌─────────┐
      │ done  │  │ failed │  │ skipped │
      └───────┘  └───┬────┘  └─────────┘
                     │ retry_count <= 上限
                     └──► pending
```

关键点：

- **僵尸回收**：`processing` 状态停留超过 15 分钟会被巡查任务重置为 `pending`。Celery 的硬超时会 kill 掉子进程，此时数据库里会留下永远不动的 `processing` 行。
- **重试上限**：`retry_count > AI_MAX_TASK_RETRIES` 后转为 `skipped`，而不是无限重试。避免一篇格式诡异的文章反复消耗 token。
- **不依赖 Celery 的重试**：重试状态记在数据库里而不是 Celery 的 retry 机制里。这样即使 Celery 的元数据丢失，业务状态依然一致；也避免了失败任务在队列里反复堆积。

## 4. 双保险的任务触发

```
文章落库 ──┬─► 直接派发 Celery 任务(最多 batch_size 个)   ← 低延迟
           │
           └─► 写 pending 记录 ──► 每 2 分钟的巡查任务    ← 不丢单
```

为什么两个都要？

- 只靠「入库即派发」：Redis 抖动、worker 重启都会丢任务，且批量导入订阅源时可能瞬间灌入上千个任务。
- 只靠「定时巡查」：最长要等 2 分钟才有摘要，演示体验差。

两者结合后：
- 派发有上限（`batch_size`），批量导入不会打爆队列
- 派发失败的记录由巡查任务兜底，最终一定会被处理
- 巡查任务本身也有硬上限，一轮最多处理 `batch_size` 条

这就是「禁止后台无限任务堆积」这条约束的具体落地方式。

## 5. 为什么分类不单独调 LLM

初版设计里 `summarizer` 和 `classifier` 是两个独立的 LLM 调用。最终合并成一次，原因很实际：

- 在自托管场景，token 就是钱。每篇文章两次调用意味着成本翻倍。
- 分类所需的语义信息（这篇文章讲什么）在生成摘要时已经拿到了，第二次调用是重复劳动。

所以现在 `classifier.py` 的职责变成：

1. 标签归一化（去噪声词、中英文去重、长度/数量限制）
2. 主题校验 —— LLM 返回了枚举外的主题时，用关键词规则兜底
3. 完全无 LLM 时的纯规则分类

`summarizer.py` 负责那唯一一次 LLM 调用，`classifier.py` 负责结果的可信化。模块边界依然清晰，但没有多余的 token 开销。

## 6. 对 LLM 输出的不信任设计

LLM 是外部依赖，输出不可控。 defensive 处理集中在 `ai/json_helper.py`：

| 风险 | 处理 |
|---|---|
| 输出裹了 ```json 代码块 | 正则剥离后再解析 |
| JSON 前后有解释性文字 | 用 `\{.*\}` / `\[.*\]` 提取最外层结构 |
| 字段名漂移（`key_points` / `keyPoints`） | `first_of()` 多候选键兜底 |
| 评分越界或非数字 | `to_int()` 收敛到 [0,10] |
| 标签数量爆炸 / 含噪声词 | `normalize_tags()` 限制数量与长度，过滤停用词 |
| 简报里编造不存在的 story_id | 与候选集合求交，不在集合内的直接丢弃 |
| 输出为空 / 无法解析 | 抛 `AIResponseError`，任务层记为 failed 稍后重试 |

## 7. 关键词匹配为什么用单词边界

一个真实踩到的坑：`"ai" in "trait"` 为 `True`。

如果关键词用朴素子串匹配，一篇讲 Rust `trait` 的文章会被判成 AI 主题，讲 `django` 的文章会被判成 Go 相关。

所以 `ai/text.py` 里做了区分：

- 含中文的关键词 → 子串匹配（中文没有词边界）
- 纯 ASCII 关键词 → `\b` 单词边界 + 大小写不敏感

分类规则和兴趣匹配共用这一套逻辑，保证行为一致。

## 8. 部署形态的取舍

上游 rssant 是一个「大单体容器」：nginx + postgres + supervisord(api/asyncapi/scheduler/worker)。
本项目改成 compose 五服务，但**没有**把上游的每个进程都拆成独立容器：

```
web        Django/gunicorn（API + 页面 + 建表）
worker     supervisord 管理三个进程：
             ├─ Celery Worker（AI 任务）
             ├─ rssant-worker（RSS 抓取执行器）
             └─ rssant-scheduler（RSS 抓取调度器）
beat       Celery Beat
redis      broker
database   PostgreSQL
```

**为什么 RSS 的三个进程合并进 worker 容器？**

在 2GB 内存下，进程数量是比「架构看起来是否纯粹」重要得多的约束。这三个进程都是后台任务，生命周期一致、扩缩容需求一致，放进同一个容器只是省掉了容器本身的开销，语义上依然是「后台任务」。如果拆成三个容器，常驻内存不会下降，反而多了三份 Python 解释器之外的容器开销。

**同时去掉了两个上游进程**：

- `asyncapi`（图片代理）：本项目未启用（前端直接走原站），它是纯可选的
- 容器内 nginx / postgres：交给独立容器，避免 supervisord 管一大堆东西

## 9. 已知限制与后续方向

诚实列出当前实现的边界：

- **技术栈偏老**：Python 3.8 + Django 2.2 是上游的技术栈，升级会破坏大量已停止维护的依赖。这是「不重写」约束下的必然结果。
- **兴趣匹配是规则，不是推荐**：没有向量检索、没有协同过滤、没有用户反馈闭环。这是刻意的 —— 在 2 核 2GB 上跑不动，也没必要。
- **前端是轻量页面**：只覆盖「看摘要 / 看简报 / 配兴趣」，没有做已读状态、离线阅读、订阅管理。订阅源管理需要走 rssant 原有的 API 或 Admin。
- **每日简报每天只跑一次**：覆盖最近 24 小时的文章，不做滚动窗口补生成。
- **单 worker 是硬约束**：AI 摘要吞吐大约每分钟 2～5 篇（取决于模型响应速度）。首次导入大量订阅源时摘要会有延迟，这是刻意用延迟换稳定性。

后续如果要继续做，优先级会是：
1. 摘要结果的缓存与复用（同 URL 不同订阅源不重复调 LLM）
2. 简报的历史归档页与订阅推送（邮件 / Webhook）
3. 把兴趣匹配升级为「关键词 + 用户反馈」的半自动权重调整
